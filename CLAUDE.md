# Project: MetaClassify (classification-api v3)

> **Naming:** the product is **MetaClassify** on GitHub / in all user-facing text
> (app title, README, docs, UI). The internal directory (`api_v3`), Python package
> (`app`), env prefix (`APIV3_`), Helm chart name and container image path keep
> their existing identifiers — renaming those would break deployments/config.

Lightweight, secure text-classification API for metadata (TF-IDF + OneVsRest
LogisticRegression, FastAPI, CPU-only, torch-free). This directory is the repo
root when published standalone.

## Tech stack
- Python >= 3.11 (Docker base + hashes lock target 3.11) · FastAPI + uvicorn · scikit-learn (sparse float32 TF-IDF word+char, solver `newton-cg`) · skops (pickle-free persistence) · pydantic-settings (env prefix `APIV3_`)

## Commands (run from the repo root)
- Test: `python -m pytest tests -q`
- Lint: `python -m ruff check app tests scripts`
- Types: `python -m mypy app --config-file pyproject.toml`
  (mypy does NOT auto-discover the config from other directories — always pass `--config-file`.)

## Conventions
- All comments, docstrings, and API texts are English; comments explain *why*, not *what*.
- Bug fixes are test-first: failing test → fix → green. Never weaken a test to pass.
- Security: no pickle (skops only); model/dataset import via file upload only (no URL fetch); user-supplied names go through `security.safe_name`; API keys compare in constant time; `APIV3_AUTH_ENABLED=false` serves loopback callers only and answers everyone else 403, a container's host included (it arrives from the bridge gateway).
- Dependencies: 17 runtime deps, pinned in `requirements.lock`; no new dependency without written justification. (The three newest — `wordfreq`, `pysbd`, `snowballstemmer` — carry `app/metadata`; the justification, and the alternatives measured and rejected, are in `docs/plans/2026-09-26-descriptive-metadata.md`.)
- Files stay under ~300 lines; split by responsibility, not by line count. A test enforces it for the three profile modules only (`tests/test_architecture.py`); every other app module past the guide states its case in its docstring, without a line count that goes stale. The admin UI is not covered by that test and holds four deliberate exceptions: `strings-de.js` and `strings-en.js` (dictionaries — a split would cut one language in half), `query.js` (one tab whose three input modes share one form, one settings builder and one answer path) and `model-detail.js` (one view of one bundle). Anything else under `app/static/ui/` that passes 300 lines is a split, not a fifth exception.
- Single-worker design: training job, model LRU cache, and rate limiter are process-local. Do not introduce multi-worker assumptions (also: Helm chart is fixed at 1 replica).

## Architecture
- `app/main.py` is only the factory: build the `FastAPI`, register the error handlers, CORS, the mounts and the routers. Its other three jobs live beside it, one reason to change each — `lifecycle.py` (the auth-configuration check that refuses an unusable deployment, the crash-recovery sweeps, the optional warmups, and the `lifespan` that orders them), `middleware.py` (the body guard — a pure ASGI class, because only there can a body be seen arriving: no body byte is read before `security.authenticate` accepts the caller, and the bytes are counted as they come, chunked included, against `max_upload_mb` for multipart and `max_json_mb` for everything else; FastAPI parses bodies before any dependency, so `require_role` alone came too late — audit 2026-09-30, S01 — and the baseline security headers; registration order is load-bearing, since Starlette runs middleware in reverse and the headers have to wrap the body guard so its 401/413 still carries them — pinned by `tests/test_api.py::test_security_headers_survive_a_short_circuited_response`; the 500 for an unhandled error is built OUTSIDE the stack by Starlette's ServerErrorMiddleware, so its handler adds `middleware.hardening_headers` itself and `count_requests` counts it before re-raising — audit 2026-09-30, R05) and `docs_content.py` (the OpenAPI description and tags, the self-hosted Swagger page, the inline favicon).
- `app/routes/*` stay thin (auth, validation, HTTP mapping) and delegate to core modules (`data`, `csv_encoding`, `dataset_load`, `dataset_stats`, `provenance`, `vectorizers`, `vocabulary`, `classifier`, `thresholds`, `tuning`, `metrics`, `prepare`, `deploy`, `training`, `train_worker`, `memory`, `capacity`, `profile_costs`, `explain`, `predict_csv`, `evaluate`, `registry`, `model_io`, `model_archive`, `model_card`, `bundle_meta`, `model_report`, `jobs`, `job_history`, `feedback`, `sharing`, `concurrency`, `correlation`, `log_filters`, `errors`), plus `feasibility` (whether a run fits its memory, called just before the fit), `stratify` (the label-stratified partition) and `limiter` (slowapi and the per-category limits).
- What several route modules need lives in `app/routes/_*.py`, which define no endpoints, so no route module imports another (a route importing a sibling makes one endpoint's module the owner of another's policy): `_bundles` (resolve a model name to a model, or stream a bundle back as a download), `_jobs` (`start_or_queue` — submit to the single worker, or 409), `_paging` (the optional `limit`/`offset` every listing takes). They sit under `routes/` and not in a core module because they raise `HTTPException` and build responses; the non-HTTP halves went the other way (`Registry.stage_export`).
- Request models live in `app/schemas/`, one module per reason to change: `training` (a run's levers), `serving` (what a prediction, explanation or correction may ask), `datasets` (evaluate/analyze/validate/export), `metadata` (the descriptive fields a text suggests on its own) and `common` (the shared wording and the blank-to-null validator). `from ..schemas import TrainRequest` still reaches them all; the fixed-shape responses stay in `responses.py`.
- Observability: `correlation.py` mints one id per request (or honours an inbound `X-Request-ID`), puts it on every log line via a filter on the ROOT handlers — so uvicorn's access and error lines carry it too — on every response, and in the sanitized 500 body, which otherwise gave the operator nothing to search the log for. `log_filters.py` redacts share ids out of those access lines (the id IS the capability). `telemetry.py` holds the request counters `/metrics` reports, keyed on the matched route TEMPLATE and never the path: keyed on the path, a URL scan could mint unbounded series in a process that never restarts. `concurrency.py` bounds how many `/predict/csv` streams may hold an anyio worker (`APIV3_MAX_CONCURRENT_CSV`), because each holds one for the whole classification out of the pool every `def` route shares.
- Profiles split three ways, one reason to change each: `profile_costs.py` (the measured cost model — a stdlib-only leaf, so read-only dataset inspection can estimate a run without loading `Settings` or `memory`), `capacity.py` (`CapacityPlan`, the part that reads `Settings`) and `profiles.py` (config.yaml parsing; the parse is cached on the file's **mtime**, so an edit still takes effect without a restart as `docs/configuration.md` promises).
- Training memory: `memory.py` is a stdlib-only leaf (RSS, cgroup limit, `PeakSampler`, `ThreadBudget` — how many head fits may run at once); `vocabulary.py` fits TF-IDF in two passes, identical to scikit-learn's `fit_transform` array for array (pinned by `tests/test_vocabulary.py` — keep it that way, a sparse `X @ w` sums a row in stored order). See `docs/plans/2026-09-11-training-memory.md`.
- Training isolation: by default (`APIV3_TRAINING_ISOLATION=process`) `train_worker.py` runs `run_training` in a child process — JSON lines over pipes, no pickle. The child only *stages* the bundle; the API process's registry *publishes* it, so there is still one disk lock. The unit suite runs trainings in-process (`thread`, pinned in `tests/conftest.py`); `tests/test_train_worker.py` covers the child path.
- Training pipeline is split by stage: `prepare.py` (load/clean/targets/split) → `deploy.py` (C-selection, thresholds, metrics, deploy fit) → `training.py` (orchestration + metadata).
- Model selection splits the same way: `thresholds.py` owns where a decision cut sits (the grid search, the URI-keyed form a bundle stores, applying them) and is a leaf that imports nothing of ours; `tuning.py` owns which `C` wins; `metrics.py` owns what a reported score means (probabilities read with the rule serving applies), shared by training and `evaluate`. `tuning` reads both — never the reverse.
- Dataset code splits by responsibility: `csv_encoding.py` = which encoding a dataset file is read in, UTF-8 or cp1252, decided ONCE from the whole file's bytes (a handful of stray bytes in UTF-8 become U+FFFD, a mixed file is refused with the byte offset) — a stdlib-only leaf every reader goes through, because deciding by trial made one broken byte turn a whole UTF-8 export into cp1252 garbage (audit 2026-09-30, T02); `data.py` = CSV reading/clean/targets/split core; `dataset_load.py` = the loader assembling a training dataset from those pieces (the one step that holds a whole dataset at once); `dataset_stats.py` = read-only inspection/statistics for the API (consumes `data`, never the reverse); `label_names.py` = what a label URI *is* and what it is called (namespace vs concept, vocabulary, URI↔display-name pairing) — a leaf that imports nothing of ours, read by `model_io`, `model_archive`, `model_report` and the repair scripts; `provenance.py` = which rows an LLM wrote or touched (data-prep's `generated_for` / `example_for` / `enriched_fields` marks) — such rows train but never validate; a leaf too. `real_rows.py` = what the marks decide for a run: the real-row split, the fallback when too few real rows exist, which labels can be scored, which are thin (reach the training minimum only through marked rows — `thin_label_threshold` decides their cut).
- The admin UI (`app/static/ui/`) is vanilla JS, no build step. It carries no text of its own: `index.html` is structure with `data-i18n*` hooks, every string lives in `strings-de.js` / `strings-en.js` (strict JSON in a one-line assignment), and `i18n.js` resolves the language (stored choice → browser preference → German) and writes it in. Keys are always literals — a key built from a template is invisible to `tests/test_ui_i18n.py`, which is what keeps both languages complete.
- `app/static/ui/escape.js` is the FIRST script the admin UI loads, and holds `esc` for that reason: the pill pickers render at construction time, before `app.js` (loaded last) has run, so a `const` defined there is not yet declared — which is why `pills.js` used to carry a verbatim second copy of the app's XSS escape. Anything a module needs at its own top level has to load before it; `latestOnly` is wrapped at the listener in `boot()` for the same reason.
- `app/markup.py` is a stdlib-only leaf holding the HTML/Markdown patterns both text pipelines need, because each composes them differently: `data.clean_text` flattens to one line of space-separated tokens (what a fitted vectorizer saw), while `app/metadata/textprep.clean_text` keeps the line breaks (a heading is a heading by standing alone on its line) and additionally drops comments and the bodies of `script`, `style`, `nav` and `footer` — each only WITH its closing tag, found in Python (code and page chrome; `header`/`aside` deliberately excluded, since the real `<h1>` is often inside a `<header>`) — takes as a tag only `<` plus a letter, `/`, `!` or `?`, removes inline tags without a space (`H<sub>2</sub>O` is H2O), normalises line endings first and decodes entities LAST (decoded first, `x &lt; 5 … y &gt; 3` was a tag that swallowed the prose between — audit 2026-09-30, M05), and judges emphasis per run (a run longer than three of the SAME marker is a rule or a form blank; a run between two word characters belongs to the word, so `arbeitsblatt_1_loesung.pdf` survives — the endpoint guarantees every word it returns occurs in the input). Those extras are deliberately NOT in the shared path, the tag rule apart: changing what `clean_text` produces in place would shift the features of every model already trained (a differential test over 1.5 M inputs pinned that when the patterns were shared), so the tag rule reached it as cleaning version 2 — new bundles record it, older ones keep version 1 (audit 2026-09-30, T09). Three rules keep it out of this project's recurring quadratic-regex trap (a 52-second `<[^>]+>` incident, and a 9.2-second heading pattern caught in review): every pattern excludes its own opening delimiter, anything otherwise ambiguous is resolved in Python rather than by backtracking (`_heading`, `_emphasis`), and tags are removed in ONE pass whose replacement function picks the replacement per match (`\n` or `" "` in the shared path, `\n` or `""` in the metadata path) — a separate block-tag pass deletes the delimiters that stop `[^<>]+` and the next pass then swallows the prose between a bare `<` and a bare `>`. Any new pattern needs a scaling measurement in `tests/test_metadata_markup.py`.
- `app/metadata/` proposes a title, a description and keywords **from the text itself** (`POST /metadata`) — a port of the default combination of `static-metadata-generators`, which measured 52 methods on two test sets. Only that default combination is ported: there is no method registry and nothing to choose between. Its only import of ours is `strip_markup_preserving_lines` from the stdlib-only `app.markup`; it reads no model, no registry and no volume, and all three generators are extractive, so every word they return occurs in the input. `textprep` (clean/tokenise/stem, distinct from `data.clean_text`, which serves the vectorizer), `sentences` (the pysbd splitter, one segmenter per thread — pysbd keeps its text on the object, audit 2026-09-30 M02), `phrases` (noun-phrase candidates + TF-IDF over German word frequencies), `budget` (character budgets), `fields` (the three methods). `tests/test_metadata_parity.py` holds it to the pipeline it came from, against a fixture generated *before* the port existed. `sentences.split_sentences` hands pysbd at most `MAX_SEGMENT_CHARS` per call: its German abbreviation pass is super-linear in the length of one call (a 100k single line took ~3 s), pinned by `tests/test_metadata_sentences.py`.
- `app/__init__.py` caps BLAS threads to 1 **before** numpy is imported — keep that the first thing the package does.
- Model bundles (format 2) = `config.json` + `metrics.json` + `head.skops` + `vectorizer.skops` + `vocabulary.json`. `config.json` records `text_cleaning`, the `data.clean_text` version the model was trained with, and serving and evaluation clean its input with that version (1 when absent; an unknown one is refused on load) — changing what the cleaning produces in place would shift the features of every trained model, so a change to it is a new version (`data.CLEANING_VERSION`; 2 since audit 2026-09-30, T09). The TF-IDF vocabularies deliberately live OUTSIDE skops: it is super-quadratic in dict entries (200k terms = ~45 min / 148 MB vs 0.3 s / 3 MB as JSON). `model_io.py` owns the pickle-free (de)serialization + skops load-safety; `bundle_meta.py` owns the forgiving typed reads of those documents (they are foreign input: reporting values degrade to absent, they never raise); `registry.py` owns the cache, disk locks and atomic publish (hidden `.name.tmp` dir + rename — made durable by `durability.py`, a stdlib leaf: every member and the staging dir are fsync'd before the rename exposes them, the models dir after; a rename alone could leave empty skops files after a power cut, audit 2026-09-30, R13); `model_report.py` owns the read-only reports over those documents (`GET /models/{name}` and `/labels`), the same seam `data` / `dataset_stats` uses; `model_archive.py` owns the ZIP form (`pack_into` streams the members from disk into a target stream, adding card + manifest; `unpack` validates an incoming archive as bytes — member allowlist, zip-bomb bound, checksums — before anything touches the filesystem), `manifest.py` the manifest itself (a SHA-256 per member, built at export, checked on import) and `model_card.py` renders the human-readable card. Export adds `README.md` + `manifest.json`; neither is kept on disk. An export is packed into a hidden staging file and streamed from there; `staged_archives.py` (a stdlib leaf) shares that file among all downloads of one bundle state and the last to finish deletes it — `Registry.stage_export` keys it by each member's size and mtime, under the disk lock (each download used to pack its own copy: twelve stalled share-link clients held twelve, audit 2026-09-30, S02).

## Deployment
- Docker: `Dockerfile` (non-root, healthcheck) · local: `docker compose up -d` (keys via `.env`).
- Kubernetes: Helm chart in `deploy/helm/classification-api` (StatefulSet, 1 replica, `/data` PVC). Changes to it are checked by RENDERING, in `tests/test_helm_chart.py`: `helm lint` reports both of the chart's guards — `required` for the API keys, `fail` for a TLS-less ingress — as `[INFO]` and exits **0**, so only `helm template` answers what a given set of values produces. The GitHub runner ships helm and GitLab's `pytest` job installs a checksum-pinned one, so that suite is a real gate in both CIs; it skips where helm is absent and refuses to skip when `CI` is set (which is why a CI job running the suite without helm fails — audit 2026-09-30, B01). The suite also renders the chart README's own install commands, because the one it documented stopped rendering the day the TLS guard landed.
- CI/CD: GitHub Actions (`.github/workflows/` — gates + GHCR image) · GitLab (`.gitlab-ci.yml` — lint/test/build/helm, credentials via CI variables only).

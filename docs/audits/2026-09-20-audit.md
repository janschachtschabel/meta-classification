## 1. Executive summary

The application's **confidentiality and integrity posture is genuinely strong** and has
improved since September 8: no path traversal, no unsafe deserialization, no auth
bypass, no secret exposure, no SSRF, no import cycles, and a supply chain (digest-pinned
base image, hash-locked transitive tree, dual `pip-audit` on every push and weekly) that
is better than most projects of this size. Nineteen of the predecessor's twenty-five
findings are closed.

The weakness is now concentrated almost entirely in **availability**, and specifically in
three controls the code documents as effective and which are not. The most serious is new
and was never in scope for any previous audit: the two text-cleaning regexes on the
serving path backtrack quadratically, and **one `/predict` request from the lowest-privilege
key freezes the whole process for 52 seconds per text — measured, not extrapolated — with
the GIL held throughout**, so the existing thread offload does not protect the event loop.
At the schema's own limit of 1000 texts per request the arithmetic reaches many hours, and
the Kubernetes liveness probe kills the pod long before that.

On the model itself the news is good: the AI-provenance rule ("rows an LLM wrote train but
never validate") holds on every path traced, the split and index-remap arithmetic is correct,
the two-pass vectorizer is provably equivalent to scikit-learn, and a seeded run is
reproducible. What needs attention there is the *reported numbers* rather than the model —
macro F1 counts unscoreable labels as 0.0 on the holdout path, so the same CSV scores
differently depending on whether data-prep's mark columns are present, and the three-way split
drifts for every non-default share.

The pattern worth naming for the team: **this codebase does not miss problems so much as it
closes them on the axis where they were first noticed.** The separator ReDoS was fixed at
the four call sites where it was found but not generalised to the other regexes on the same
request path; the `/tmp` spill was fixed for writability but not for boundedness; uvicorn's
`--proxy-headers` was added to the image but the trusted-proxy list never reached the chart,
which leaves the flag inert. Each remaining gap is the untouched half of a problem that was
already understood.

**Single most important action:** replace the two character classes in `app/data.py:43-44`
and add a regression test. It is a two-line change that removes a one-request, full-outage
denial of service.

## 4. Verdict: **Conditional**

The API as deployed is sound in everything that concerns confidentiality and integrity, and
its supply chain, container hardening and test discipline are above the norm. It is **not**
ready to face an untrusted network until three things are done:

1. **SEC-1 (blocking).** Fix the two regexes in `app/data.py:43-44`. Until then any holder
   of a readonly key — the key handed to editors — can take the service down with one
   request, and in Kubernetes can hold it down in a crash loop. This is a two-line change;
   the only care needed is the behaviour caveat documented under SEC-1.
2. **SEC-2 and SEC-3 before external exposure.** The upload cap does not bound what reaches
   disk, and the shipped chart's rate limiter attributes every request in the cluster to one
   address. Both are the untouched halves of problems earlier audits identified.
3. **OPS-2 before the next production deploy.** A bad `main` deploy currently cannot be
   reverted with `helm rollback`, because both revisions resolve to the same mutable tag.

Everything else on this list is improvement work, not a gate. For an internal deployment
behind a trusted network and a trusted editorial user base, only condition 1 is genuinely
urgent — but it is urgent there too, because an accidental paste of markup-heavy text is
enough to trigger it without any malice.

## 5. Top issues

### SEC-1 · 🔴 Critical — quadratic backtracking in `clean_text` freezes the whole process

- **File / Lines:** `app/data.py:43-44`, applied at `:58-59`; reached on every serving
  path via `app/classifier.py:105`.
- **Problem:** `_HTML_TAG_RE = re.compile(r"<[^>]+>")` and
  `_MD_LINK_RE = re.compile(r"!?\[([^\]]*)\]\([^)]*\)")` both backtrack quadratically on
  input made of unclosed `[` or `<`. Each start position consumes to the end of the string
  before failing, and there are *n* start positions.
- **Measured (independently, on this checkout):** 2,500 chars 0.05 s · 5,000 chars 0.20 s ·
  10,000 chars 0.67 s · 20,000 chars 2.69 s · 40,000 chars 10.3 s — a clean 4× per
  doubling — and **52.4 s for a single text at the schema's own 100,000-character maximum**
  (`app/schemas/serving.py:18`). A benign text of the same length takes 0.001 s.
- **Why the offload does not help:** a heartbeat thread was starved for the entire
  duration of the match (2.27 s gap against an 0.011 s idle baseline), i.e. the GIL is held
  throughout. The `await asyncio.to_thread(...)` at `app/routes/predict.py:130` moves the
  work off the loop's *thread* but not off the loop's *interpreter*.
- **Impact:** total availability loss from **one** request carrying the **lowest-privilege**
  credential — `/predict` is `require_role("readonly")`, the key handed to editors. The rate
  limiter cannot help because one request suffices. `/predict`, `/predict/batch`,
  `/predict/multi`, `/predict/explain` and `/predict/csv` all reach it. The schema permits
  1000 texts per request, so the arithmetic runs to hours. Under the shipped Helm chart the
  liveness probe (`periodSeconds: 30`, `failureThreshold: 3`) kills the pod after ~90 s,
  taking any running training with it — a crash loop on demand.
- **The bitter part:** the comment directly above the bound at `app/schemas/serving.py:16-17`
  states that it exists so "a single request cannot exhaust the single worker's RAM/CPU".
  The measurement falsifies that claim.
- **Fix:** exclude the opening delimiter from each character class, so a start position
  fails in O(1) instead of O(n):
  ```python
  _HTML_TAG_RE = re.compile(r"<[^<>]*>")
  _MD_LINK_RE = re.compile(r"!?\[([^\[\]]*)\]\(([^()]*)\)")
  ```
  Verified: the same inputs then take 0.0017 s and 0.0039 s at 80,000 characters.
- **⚠ The fix is not behaviour-preserving on nested or unbalanced markup, and this matters.**
  I diffed old against new on realistic input: five of seven samples are identical, two differ —
  `'<tag with <nested> bracket>'` (old `'  bracket>'`, new `'<tag with   bracket>'`) and
  `'[text](url(with)parens)'` (old `'textparens)'`, new unchanged). `clean_text` runs at
  **training** time too, so changing it introduces a train/serve skew for texts containing
  nested markup unless models are retrained. The skew is small (TF-IDF over word and char
  n-grams) and confined to malformed markup, but it is a real change and must be stated in
  the CHANGELOG rather than shipped as a silent bug fix. Add a regression test asserting
  `clean_text("[" * 50_000)` completes in well under a second, and pin the new behaviour on
  the two nested cases.
- **Belt and braces, independent of the regex change:** bound the *total* characters per
  request (`sum(len(t) for t in texts)`), not only the per-text and per-list counts.

### SEC-2 · 🟠 High — the upload cap runs after the body is already on disk

- **File / Lines:** `app/security.py:94-141`; callers `app/routes/predict_bulk.py:129`,
  `app/routes/datasets.py:210`, `app/routes/models.py:245`.
- **Problem:** FastAPI resolves `UploadFile` during dependency injection, so the multipart
  body is fully parsed *before* the route body runs. In the installed Starlette,
  `max_part_size` is enforced only for non-file parts; a file part streams unbounded into a
  `SpooledTemporaryFile` that rolls over to the system temp directory.
  `APIV3_MAX_UPLOAD_MB` therefore bounds only the *second* copy, the one written into the
  data directory.
- **Impact:** `POST /predict/csv` is **readonly**-authenticated at 300/min, so a
  low-privilege key can push arbitrary volume into the temp directory. The chart mounts
  `/tmp` as an `emptyDir` with **no `sizeLimit`**, which is node ephemeral storage — so this
  escalates past the pod to node-pressure eviction. Only the ingress annotation
  `proxy-body-size: "200m"` limits it today, and `docker-compose.yml` has no proxy at all.
- **History:** the mechanism was already described in the 2026-07-16 audit — as a
  *functional* break (a read-only root filesystem meant uploads over 1 MB failed). The
  remediation mounted the `emptyDir`, which unblocked the write without bounding it. The
  earlier fix converted "uploads are broken" into "uploads are unbounded".
- **Fix:** reject on `Content-Length` in an ASGI middleware, before the form is parsed —
  one place covers all three upload routes — and set `sizeLimit` on the `tmp` emptyDir.

### SEC-3 · 🟠 High — rate limiting collapses to one global bucket in the shipped chart

- **File / Lines:** `app/limiter.py:18` (`key_func=get_remote_address`); `Dockerfile:39-43`;
  `FORWARDED_ALLOW_IPS` appears **nowhere** under `deploy/` (grepped).
- **Problem:** uvicorn honours `X-Forwarded-For` only when the TCP peer is in
  `forwarded_allow_ips`, default `127.0.0.1`. Behind the chart's own nginx ingress the peer
  is the ingress-controller pod, so the header is discarded and every client resolves to one
  address.
- **Impact:** `rate_limit_predict: "300/minute"` becomes 300/min for the whole world; one
  client silently denies `/predict` to everyone else. The comment at `app/routes/share.py:62`
  ("public endpoint: throttle share-id brute-forcing") describes per-client throttling that
  does not exist. The inverse misconfiguration is worse: an operator reaching for
  `config.extraEnv` with `FORWARDED_ALLOW_IPS=*` lets any client spoof the header and bypass
  the limiter outright.
- **History:** raised in the 2026-07-06 audit, ranked as fix T3 in 2026-07-16. Half landed
  (`--proxy-headers` in the Dockerfile); the trusted-proxy list never reached the chart, so
  the flag is inert.
- **Fix:** template `FORWARDED_ALLOW_IPS` into `configmap-env.yaml` from a required value
  (the ingress controller's pod CIDR) and document that `*` is not acceptable. Keying the
  limiter on the API key instead of the IP sidesteps the proxy question entirely.

### API-1 · 🟠 High — `GET /feedback/export` is unbounded, in memory, and on the event loop

- **File / Lines:** `app/routes/feedback.py:52-72`; `app/feedback.py:87-113` (`read_all`),
  `:116-135` (`to_csv`), `:46-84` (`append`).
- **Problem:** the handler is `async def` and calls `feedback_store.to_csv()` inline.
  `to_csv` → `read_all` → `path.read_text()` slurps the entire append-only JSONL, builds a
  full list of dicts, then a complete CSV string, which FastAPI holds as one body. No limit,
  no cursor, no size cap. The store is *deliberately* uncapped (`app/feedback.py` docstring:
  "this is training data, not a log"), so it grows for the life of the volume.
- **Impact:** one export pins the single worker's event loop for the entire read and holds
  three copies of the file in memory. `/health`, `/predict` and everything else stall.
- **Fix:** `StreamingResponse` over a line-by-line generator via `iterate_in_threadpool`;
  add `limit` / `since=<recorded_at>`; add a ceiling in `append` that answers 507 rather than
  filling the volume.

### SEC-4 · 🟠 High — `FeedbackRequest`'s bounds do not bound what they claim to

- **File / Lines:** `app/schemas/serving.py:125-140`; route `app/routes/feedback.py:19-49`.
- **Problem:** `predicted: list[str] = Field(default_factory=list, max_length=100)` and
  `corrected` likewise. In pydantic v2, `max_length` on a list field bounds the **list
  length**, not the items; the inner `str` carries no bound, unlike `text` (100,000) and
  `source` (50).
- **Demonstrated:** `FeedbackRequest(text="t", model_name="m", predicted=[<1 MB>],
  corrected=[<1 MB>])` is **accepted**, carrying 2,000,001 characters in one request. A list
  of 101 items is correctly rejected, so the bound that *was* written works — it is simply
  not the bound the docstring promises.
- **Why it matters:** the class docstring states "The bounds are the point: this is the only
  write a *readonly* key can make, so they are what stands between a key and an unbounded
  file on the volume." That guarantee is false for the two list fields. The route is
  `require_role("readonly")` at 120/min, the file is uncapped, and its contents are later
  consumed as training data — so this is a volume-exhaustion *and* a data-poisoning channel.
- **Fix:** `predicted: list[Annotated[str, Field(max_length=500)]] = Field(default_factory=list,
  max_length=100)`, the same for `corrected`, plus a size ceiling or rotation policy for the
  file.

### PERF-1 · 🟠 High — cheap read routes block the event loop on the registry's disk lock

- **File / Lines:** `app/routes/models.py:106` (`registry.info`), `:127`
  (`label_diagnostics`), `app/routes/predict_bulk.py:54` — all inside `async def` handlers,
  calling straight through; the lock is taken at `app/registry.py:243-247`.
- **Problem:** those methods take `Registry._disk_lock`. That lock is held for **seconds**
  by `export_to` (its own docstring: "a few seconds of extra hold on a 50 MB bundle"), by
  `import_zip`, by a cold cache miss, and by `delete`'s rmtree. Because the handler is
  `async def`, it is the **event loop thread** that blocks on `threading.Lock.acquire()`.
- **Why it stands out:** every heavy caller in the same files is already offloaded
  (`models.py:154,170,205,248`, `share.py:83`, `predict.py:130,186,215`,
  `predict_bulk.py:118,132`). The light readers were left on the loop and contend on the
  same lock.
- **Impact:** a single `GET /models/{name}` issued while a 180 MB export runs freezes
  `/health`, `/metrics` and every in-flight request for the duration of the zip.
- **Fix:** `await asyncio.to_thread(...)` at those three call sites and for
  `registry.list()` (`models.py:80`, `system.py:50`).

### OPS-1 · 🟠 High — the pipeline that builds the production image has no vulnerability gate

- **File / Lines:** `.gitlab-ci.yml` — jobs are `ruff check`, `helm lint`, `mypy`, `pytest`,
  three build-and-push jobs. **Zero** occurrences of `pip-audit` (grepped).
- **Problem:** the GitLab pipeline pushes to `docker.edu-sharing.com/projects/wlo/classification-api`,
  which is exactly what the Helm chart deploys (`values.yaml:37-39`). GitHub's two audit jobs
  gate the *ghcr.io* image, which is not what production runs.
- **Why it matters concretely:** `ci.yml:100-101` names the instance this catches —
  "anyio 4.14.1 sat pinned here with three CVEs while that scan was green (2026-09-19)".
  That class of finding has no chance of blocking the GitLab build.
- **Fix:** add a `pip-audit` job to the `test` stage (so it gates `build`), running the same
  `--require-hashes --disable-pip` scan over `requirements-hashes.lock`.

### OPS-2 · 🟠 High — branch deploys have no rollback target, and the chart ships `appVersion: "latest"`

- **File / Lines:** `.gitlab-ci.yml:135-136`, `:198-199`;
  `deploy/helm/classification-api/Chart.yaml:11`; `values.yaml:33` (`pullPolicy: IfNotPresent`).
- **Problem (a):** a `main` deploy produces image tag `main` and chart appVersion `main`, so
  Helm revisions N and N−1 resolve to the **same mutable tag**. `helm rollback` restores
  values and re-deploys `…:main`; with `IfNotPresent` a node that cached `main` never
  re-pulls. Tag releases (`v1.2.3`) are immutable and roll back correctly — the gap is
  branch deploys, which is the default flow.
- **Problem (b):** `Chart.yaml:11` is `appVersion: "latest"`, so any `helm install` that does
  not go through the CI `--app-version` override resolves to `…:latest`. Every other artifact
  in this repo is deliberately pinned — the base image by digest, the Actions by SHA, the CI
  images by exact tag with a comment explaining why `latest` is unacceptable.
- **Fix:** push an immutable `sha-$CI_COMMIT_SHORT_SHA` tag alongside the branch slug and set
  `APP_VERSION` to it; set `Chart.yaml`'s `appVersion` to the released version (`3.2.0`).

### OPS-3 · 🟠 High — the readiness probe proves only that the process answered

- **File / Lines:** `deploy/helm/classification-api/templates/statefulset.yaml:77-87`
  (readiness → `/health`), and the same endpoint for startup and liveness;
  `app/routes/system.py:23-26` returns a hardcoded literal.
- **Problem:** all three probes hit one endpoint that checks no dependency — not the PVC,
  not the models directory, not the cache. The failure modes this deployment actually has are
  exactly the ones `/health` cannot see, and warmup failure is *deliberately* swallowed
  (`app/main.py:36-37`) — correct for startup, wrong for readiness.
- **Impact:** the pod goes `Ready` and receives traffic while every `/predict` returns 500,
  and neither the probe nor the six exported gauges will say so.
- **Fix:** keep `/health` static for liveness; add a `/ready` that stats the data and models
  directories and, when `warmup_models` is configured, asserts at least one model is resident;
  point `readinessProbe` at it.

### FE-1 · 🟠 High — the declared border token fails SC 1.4.11 in both themes

- **File / Lines:** `app/static/ui/style.css:17` (light), `:33` (dark); consumers at
  `:75, :94, :111, :113, :155, :174, :208`.
- **Problem:** `--border: #c3ccd6` carries the inline comment ">3:1 vs surface for field
  borders". **Computed:** 1.62:1 against `--surface` `#ffffff` and 1.50:1 against the field
  fill `--bg` `#f4f6f8`. Dark mode `--border: #46525f` is 1.98:1 and 2.27:1. All four fail
  the 3:1 that SC 1.4.11 requires for the visual boundary of a UI component. Every other
  declared token's comment is accurate — I checked all of them; `--text`, `--muted` and
  `--accent` pass in both themes.
- **Impact:** this token draws every input, select and textarea border, every card, every
  fieldset, the topbar rule and every table row separator. Low-vision users cannot see where
  form fields begin. In a BITV 2.0 / EN 301 549 context this is a conformance blocker, and the
  false comment means the next reviewer will trust it and move on.
- **Fix:** light `≈ #6b7684`, dark `≈ #78838f`. If the softer line is wanted for cards and
  rows, split into `--border-ui` (3:1, controls) and `--border-hairline` (decorative), and
  correct the comments to measured values.

### DEP-1 · 🟠 High — `starlette` is imported directly, declared nowhere, and already diverged

- **File / Lines:** `app/routes/models.py:29` and `app/routes/predict_bulk.py:21`
  (`from starlette.background import BackgroundTask`). Absent from `requirements.txt`,
  `requirements.lock` and `pyproject.toml`.
- **Verified:** `requirements-hashes.lock` pins `starlette==1.3.1` (what the image and CI
  install); this checkout's dev venv holds **1.6.0**. Three minor versions apart, today.
- **Why it matters:** `pyproject.toml` already legislates for exactly this case for joblib —
  *"Imported directly … declared so the version is pinned/tested instead of riding along

  files or a 500 on download, reproducing only in dev or only in production depending on

  exact versions the test suite ran against".

### Logic & correctness

- 🟠 **CORR-1** `evaluate` materialises a whole dataset's probabilities in the **serving**
  process, unchunked and unbudgeted. `app/evaluate.py:83` builds one dense
  `(n_rows, n_labels)` array for the entire dataset, and `compute_metrics` →
  `apply_thresholds` allocates a second one. `app/routes/models.py:306` submits
  `run_evaluation` through `job_runner.submit` **without** `run_in_child`, while training at
  `app/routes/training.py:164-165` chooses the child process by default — precisely so an OOM
  kill ends the run and not the server. `predict_csv.py` chunks the identical "score a whole
  CSV" operation at 500 rows; `evaluate` got neither treatment. A 300k-row evaluation against
  a 300-label model needs ~1.4 GB of decision matrices alone, in the API process, invisible to
  `ThreadBudget` and to `refuse_if_the_run_cannot_fit`. **Fix:** chunk it like `predict_csv`,
  and either route evaluations through `run_in_child` too or add the feasibility gate.
- 🟡 **CORR-2** macro F1 counts labels the split cannot score as 0.0 — but only when the
  dataset has **no** provenance marks. `app/deploy.py:171` passes
  `scored=prep.provenance.scored if prep.provenance else None`, and `app/metrics.py:65-70`
  narrows `labels=` only when `scored` is not None. **Demonstrated:** a *perfect* prediction
  over three labels where one has no positives in the split scores **0.667** macro instead of
  1.000. The same narrowing already exists and is applied for marked datasets, so the identical
  CSV reports a **higher** macro with mark columns than without — exactly the
  non-comparability `app/real_rows.py:85-86` says it wants to prevent.
  *Downgraded from the reviewer's High:* it is confined to the **holdout** path. The default
  profile is `auto` (cv_folds 3) and `best` (5) are k-fold, where every real row validates
  out-of-fold so every label with a positive row is represented; and both set
  `stratified_splits: true`. The exposure is the `fast` profile — `cv_folds: 0`, no
  stratification — and custom profiles that leave `cv_folds` unset. **Fix:** compute the
  present-label mask unconditionally in `prepare` and intersect it with the provenance mask
  when one exists; record the excluded labels the way `labels_not_validated` already is.
- 🟡 **CORR-3** the three-way split drifts for every non-default share.
  `app/data.py:219-222` chains two `train_test_split` calls and takes `ceil` twice.
  **Measured on n=100:** `0.15/0.15` → 70/15/15 (exact), but `0.1/0.2` → 69/10/**21**,

  the test split can come out a fifth larger than asked for. **Fix:** compute all three sizes
  once from `n` and slice one shuffled permutation.
- 🟡 **CORR-4** the AI-row fallback triggers only on an *empty* validation/test split, not a
  degenerate one. `app/real_rows.py:51-52` accepts one row in each as a real split with
  `fallback=None`; `:41-43` accepts three real rows for three folds. The bundle then reads
  "holdout train/val/test split (metrics on the untouched test split)" and
  `validated_on: "real_rows"` for an F1 computed on a single row, with per-label thresholds
  tuned on another single row — and the `fallback` field, the UI warning and the
  "not meaningful" hint all stay silent. **Fix:** fall back (with the reason) below a
  meaningful minimum, or add a second reason string that flags the shortage without switching
  to the all-rows fallback.
- 🟡 **CORR-5** an unreadable RSS silently means "nothing is held", which is the optimistic
  direction. `app/memory.py:102-119` returns `0` on any platform it cannot read, and
  `threads_within` / `refuse_if_the_run_cannot_fit` treat that as *a measurement of zero* —
  granting the maximum thread count and passing the cgroup gate the whole design exists to
  enforce. The module docstring says readings "degrade to 'unknown' (0 / None)"; downstream,
  0 is not unknown. No log line says the budget is flying blind. **Fix:** return `int | None`
  and either skip the check or warn once.
- 🟢 **CORR-6** bad split configuration surfaces as a 500, not a configuration error:
  with `validation_size + test_size >= 1.0` sklearn's own `InvalidParameterError` escapes
  `split_rows`'s `except ValueError` (which wraps only the `train_only` branch), so it is
  sanitized to "Training failed; see server logs".
- 🟢 **CORR-7** three `zip(..., strict=False)` calls pair a label list against a per-column
  array whose lengths are a pipeline invariant (`thresholds.py:119`, `prepare.py:84`,

  global threshold instead of raising. The codebase uses `strict=True` exactly where it
  matters elsewhere, so the inconsistency reads as accidental.
- 🟢 **CORR-8** the select→tune→score policy is implemented twice, once per evaluation mode

- 🟢 **CORR-9** `TfidfBackend.fit()` (`app/vectorizers.py:105-113`) bypasses

### Performance

- 🟠 **PERF-1** cheap read routes block the event loop on the disk lock (above).
- 🟡 **PERF-2** `/predict/csv` can exhaust the shared threadpool. The `StreamingResponse`
  wraps a **sync** generator, so Starlette iterates it through `iterate_in_threadpool` and
  each in-flight request holds one anyio worker for the whole classification (minutes for a
  200 MB CSV). That pool is the same one every `def` route and every `asyncio.to_thread` call
  uses; nothing bounds concurrency, and the limit is per client address with a readonly key.
  **Fix:** a shared `CapacityLimiter` sized from `effective_n_jobs`, rejecting over it with
  429/503 instead of queueing.
- 🟡 **PERF-3** the event loop waits on locks a background thread owns:
  `job_history.recent` (`training.py:273`, `async def`) takes the same lock the runner thread
  holds across a full read-modify-rewrite; `POST /feedback` does blocking file I/O on the loop.
  Bounded (200 records, one writer), so not High.
- 🟢 **PERF-4** `ClassifierModel._baseline` is lazily filled on a cache-shared object, so two
  concurrent first requests both compute it. Deterministic, so the race is benign — the cost
  is duplicate cold passes.
- 🟠 **PERF-5** the threshold search burns minutes on Python call overhead.
  `app/thresholds.py:69-97` runs 19 full `f1_score(average="macro")` passes over the whole
  `(n, L)` matrix, plus `n_labels × 19` separate single-column `f1_score` calls — and with
  `select_c_on_tuned_thresholds=True` (the default) the whole search runs once **per C
  candidate**. Measured in this venv: 5.9 s at 25,000×48, **43.1 s at 156,373×60** (the
  README's own anchor shape) and 140 s at 100,000×300 — times a 3-value grid, that is ~129 s
  of the 40.2-minute anchor run and **~7 minutes** on a 100k×300 target. It grows linearly in
  rows × labels × grid, i.e. exactly where the project is heading. **Fix:** one vectorised
  sweep per column — sort the scores once, take cumulative true positives, evaluate the 19
  cuts with `np.searchsorted`.
- 🟡 **PERF-6** the k-fold out-of-fold buffers are invisible to the feasibility gate, and
  they are the term that grows fastest. `app/tuning.py:215` allocates `|c_grid|` full
  `(rows, labels)` float32 arrays up front and holds them all; `refuse_if_the_run_cannot_fit`
  weighs only `head + targets + matrix + copies`. At 250,000 rows × 300 labels × 3 candidates
  that is **0.90 GB** against 0.07 GB of targets — and the gate's own docstring says it exists
  for the wide-label regime. A CV run there passes the gate and is then OOM-killed, reaching
  the operator as `exit code -9`: the exact failure the gate exists to replace with a message.
  **Fix:** add `len(rows) * n_labels * 4 * len(c_grid)` to `needed` for `cv_folds >= 2`, or
  keep only the current and best candidates' buffers.
- 🟡 **PERF-7** every decision matrix is int64 — twice the float32 probabilities it derives
  from. **Verified:** a 1000×50 float32 `proba` of 200,000 bytes yields a 400,000-byte int64
  prediction matrix, for a 0/1 array (`app/thresholds.py:149` `np.zeros_like(proba,
  dtype=int)`, and five sibling sites). This is the same mistake `data.prepare_targets` goes
  to great lengths to avoid — its docstring explains that int8 is used because "sklearn's
  default int64 would spend 8 bytes per bit — 1.34 GB at 600k rows × 300 labels versus
  168 MB". At 250,000×300 one such cast is 600 MB transient, allocated and freed 19 times in
  the global threshold loop, in the middle of the phase the memory budget is protecting.
  **Fix:** `astype(np.int8)` in all six places; scikit-learn treats int8 indicator matrices
  identically.
- 🟢 **PERF-8** `stratified_partition` re-materialises the whole unplaced label block once
  per label (`app/stratify.py:78`). Measured 6.3 s at 50,000×300 and 11.6 s at 100,000×300 —
  real but small against a 40-minute run, plus ~90 MB of allocator churn per iteration.
  **Fix:** maintain the `remaining` counts incrementally instead of recomputing from a copy.
